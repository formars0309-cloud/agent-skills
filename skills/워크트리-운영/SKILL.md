# 워크트리 운영 — 조율자 절차

여러 저장소의 AGENTS.md에 반복되던 운영 규칙을 한 벌로 모은 것이다. 저장소별 규칙이
이 문서와 충돌하면 저장소 쪽을 따른다. 명령 상세는 `orca-cli` 스킬
(`orca skills get orca-cli`), 결과 회수 대기는 `task-wait` 스킬을 본다.

## 작업 넘기는 법

**넘기기 전에 갖춰야 할 것.** 워커에게는 스스로 완료를 판단할 수 있는 명세를 준다.
무엇을 바꿀지, 어떤 파일인지, 무엇으로 검증하는지(보통 테스트 명령)를 명시한다.
요구사항이 흐릿하면 넘기기 전에 조율자가 먼저 확정한다.

새 워크트리에 워커를 띄우는 경우:

```
orca worktree create --name <작업이름> --agent codex --prompt "<작업 명세>" --json
```

이미 떠 있는 워커에게 추가 지시를 보내는 경우:

```
orca terminal send --terminal <handle> --text "<지시>" --enter --json
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 300000 --json
```

**함정 두 가지 — 검증된 사항이다.**

1. `orca orchestration send`는 워커 우편함에 넣기만 한다. idle 상태인 워커는 우편함을
   폴링하지 않으므로 그대로 멈춰 있다. 조율자가 `orca terminal send`로 직접 깨워야
   한다. 자동 이벤트 루프는 없다.
2. 태스크 `--spec`은 Orca가 주입하는 워커 프로토콜을 덮어쓴다. "정확히 X만 답하고 그
   외에는 아무것도 하지 마라" 같은 명세를 주면 워커가 필수 `worker_done` 보고까지
   건너뛰어 태스크가 `[dispatched]`에 영영 묶인다. 완료 보고를 막는 명세를 쓰지 않는다.

넘긴 뒤에는 결과를 그대로 신뢰하지 말고 검토한 다음 머지 여부를 정한다.

## 워크트리 다루기

Orca는 워크트리를 `<repoId>::<절대경로>`로 식별한다. **경로가 곧 ID다.**

- `git worktree move`로 폴더를 옮기면 Orca 메타데이터가 옛 경로를 가리켜 카드가 깨진다.
  폴더명을 바꾸려면 워크트리를 지우고 다시 만드는 수밖에 없다.
- 이름을 맞추는 게 목적이면 `git branch -m`(브랜치)과
  `orca worktree set --display-name`(카드 이름) 쪽이 안전하다. 폴더·브랜치·표시 이름
  셋을 일치시켜 둔다.
- 워크트리를 지우기 전에 `orca worktree ps --json`으로 `liveTerminalCount`를 확인한다.
  실행 중인 에이전트 세션이 함께 사라진다.

raw `git worktree` 대신 `orca worktree` 명령을 쓴다.

## 백그라운드 워크트리 관리

여러 워크트리에서 에이전트가 동시에 도는 것이 기본 운영 방식이다. 조율자는 그것을
감시하다가, **작업이 쉬는 워크트리만** 골라 커밋·푸시로 안전하게 만든다.

### 휴지 판정 — 1시간 규칙

터미널 활동과 파일 쓰기가 **모두 60분 이상 멈춘** 워크트리를 "작업을 잠시 쉬는 중"으로
본다. 둘 다 봐야 한다. 터미널만 보면 에이전트가 말없이 파일만 쏟아낼 때 놓치고, 파일만
보면 사람의 입력을 기다리는 상태를 구분하지 못한다.

짧은 임계(5분)는 쓰지 않는다. 실측에서 계속 오탐이 났고, 진행 중인 재구성을 중간
상태로 커밋할 뻔했다.

### 커밋 전 검토

휴지로 판정돼도 바로 커밋하지 않는다. 순서대로 확인한다.

1. **정말 멈췄나** — 파일 목록을 두 번 확인해 사이에 늘어나지 않는지 본다.
2. **정합성** — 삭제된 모듈을 아직 import 하는 곳이 없는지 등.
3. **테스트** — 있으면 돌린다. 대규모 재구성은 테스트 통과가 완결의 증거다.
4. **비밀 정보** — 자격증명 패턴, 키스토어·인증서 파일, 개인 이메일을 훑는다.
   배포 설정 작업에서 특히 중요하다.
5. **스테이징 범위** — `node_modules`나 대용량 산출물이 섞이지 않는지 본다.

애매하면 커밋하지 않고 사용자에게 묻는다. 커밋은 되돌릴 수 있지만, 중간 상태를 커밋해
다른 에이전트의 흐름을 끊는 건 되돌리기 번거롭다.

### 푸시

- 브랜치가 갈라졌으면(`behind` > 0) **강제 푸시하지 않는다.** 사용자 승인을 받고,
  실행할 때는 `--force-with-lease`를 쓰고 사라질 커밋을 백업 브랜치로 먼저 보존한다.
- 작업 중인 워크트리의 커밋을 성급히 푸시하지 않는다. 에이전트가 그 커밋을 amend 하면
  갈라짐이 생긴다. 실제로 한 번 발생했다.
- 업스트림이 없으면 `git push -u origin <브랜치>`로 설정한다.
- 리모트 자체가 없으면 커밋까지만 하고, 저장소 생성은 사용자에게 확인받는다.

### 병렬의 한계

구현은 병렬로 돌리고, **판단은 직렬로 한다.** 자동 검증(테스트·QA 스크립트)이 대신
판단해주는 작업은 여러 개를 동시에 둬도 되지만, 사람의 판단이 매 단계 필요한 작업
— 특히 의료 콘텐츠 발행 — 은 동시에 하나만 진행한다.
